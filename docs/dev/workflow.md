# Порядок работы

Эти правила особенно важны для автономной работы (облачная сессия, ночная работа без автора).

## Ветки и коммиты

- Работа над этапом — в ветке `stage-N/<короткое-имя>`, например `stage-1/core`.
- Коммиты маленькие и законченные: одна система, один закон, одна группа тестов.
- Каждый коммит проходит `pnpm check`.
- Сообщения коммитов — по-английски, в повелительном наклонении: `Add thermal system with fire spread`.

## Решения и допущения

- Любое техническое решение, которое не записано в `docs/dev/`, записывается в [decisions.md](decisions.md).
- Любое **допущение о дизайне игры** (когда в `docs/` нет ответа) записывается туда же с пометкой `ДОПУЩЕНИЕ`. Автор просматривает их утром.
- **Дизайн-документы (`docs/*.md` вне `dev/`) не переписывать.** Можно только:
  - исправить явную опечатку;
  - добавить пункт в [../13-open-questions.md](../13-open-questions.md), если найден новый открытый вопрос.

## Отчёт

В конце сессии написать отчёт `docs/dev/reports/YYYY-MM-DD-stage-N.md`:

1. **Что сделано** — список с ссылками на файлы.
2. **Как проверить** — точные команды.
3. **Что не сделано и почему.**
4. **Допущения** — ссылки на записи в `decisions.md`.
5. **Что заметил** — где дизайн оказался противоречивым или неудобным для кода. Это самое ценное для автора.
6. **Что предлагаю дальше.**

Отчёт пишется для автора, который не программист по основной работе и устал: коротко, по-русски, без жаргона там, где можно без него.

## Чего не делать

- Не начинать следующий этап, пока текущий не закончен.
- Не устанавливать зависимости из «позже» в [stack.md](stack.md).
- Не делать графику на этапе 1.
- Не отключать и не ослаблять тесты, чтобы они прошли.
